# ProofFlow 与论文 v0.14 对齐的升级要求

- 状态：下一版本规范基线，不代表 `0.1.0-alpha.4` 已经实现。
- 理论来源：`From_Prompt_to_Proof_v0.14.md`，证据快照日期为 2026-08-03，
  SHA-256 为 `bc82eac917dbebc95075f54da6c6b45616d13727ec82dd9d4d12b06f7d56bfb6`。
- 建议目标版本：`0.1.0-alpha.5`。

## 1. 文档目的

论文 v0.14 把“保存研究轨迹”进一步拆成三项不同能力：

- **M1 轨迹保留**：保留失败路线、工件、脚本、异议和未完成义务；
- **M2 转移接受**：记录什么证据或权限接受了状态变化；
- **M3 延续与交接控制**：记录下一次有界行动为什么运行、等待、转向、请求人工或停止，以及接收者需要恢复的范围和证据。

Alpha.4 已经较强地覆盖 M1，但不能由“事件已经保存”推导出 M2 或 M3 已完成。本文件把论文的描述性理论转成可审计的软件要求，同时继续坚持以下产品宪法：

- 不保证解题，不把模型自述当作数学事实；
- `UNRESOLVED`、失败、无变化和请求人工都是合法结果；
- 不要求或保存私有思维链；只记录可观察的候选、测试、缺陷、修复、验证和发布事件；
- 新状态必须通过追加事件建立，不重写既有历史；
- SQLite、仪表盘、报告和论文叙述都是可重建投影，不得覆盖规范证据。

## 2. 规范性升级要求

以下标识用于架构、实现、测试和验收之间的追踪。

### PF-014-01：四个状态平面

每个研究项目必须能分别表达：

1. **Operational State**：下一项有界行动的所有者、阻塞、门禁、配额和是否允许继续；
2. **Epistemic State**：已知、排除、保留、不确定、重述和可复活的知识；
3. **Claim State**：精确命题当前获得何种证据支持、反驳、审查和成熟度；
4. **Artifact State**：工件处于草稿、损坏、候选、修复、被替代、发布或撤回中的哪一状态。

一个平面的变化不得隐式改变其他平面。例如，Lean 构建成功不能自动证明自然语言目标绑定正确；仓库更新也不能自动升级数学声明。

### PF-014-02：观察、提案、接受和写回分离

工具输出、模型自述、编译器错误、外部来源更新和人工偏好首先都是观察或转移提案。规范状态只能由经过验证的接受事件改变。

最小 `ResearchStateTransition` 应包含：

- `from_revision` 与四平面原状态摘要；
- `trigger_class` 和 `trigger_evidence_refs`；
- `proposal_actor_ref`；
- `acceptance_actor_or_mechanism_ref`；
- 四平面的 `accepted_delta`；
- `rejected_or_unaccepted_components`；
- `next_obligation_refs` 和 `handoff_refs`；
- `visibility`：直接观察、公开轨迹推导、作者报告或尚未建立；
- 幂等键和预期修订号。

无接受依据、引用不存在、修订已过期或状态约束不满足时必须拒绝写回。

### PF-014-03：类型化延续合同

每个自动或人工研究回合结束时必须产生一个类型化决定：

- `RUN_NEXT`：满足继续条件，允许下一次有界行动；
- `WAIT`：等待外部状态、工具或审查；
- `REDIRECT`：保留旧路线并转向新路线；
- `ASK_HUMAN`：需要人工判断，不能用旁支工作绕过；
- `STOP`：达到终止条件或没有获准继续；
- `NO_CHANGE`：本轮没有形成被接受的状态增量。

决定必须引用接受后的修订号、理由、门禁、预算影响和下一接受谓词。定时器、模型自述或单纯“又生成了文件”不能自动授权继续消耗配额。

### PF-014-04：证据化交接包

交接不能只是一段自由文本。`HandoffPacket` 至少绑定：

- 转移范围与目标声明原子；
- 可访问的工件及其哈希；
- 已建立事实与其证据；
- 已失败路线、失败见证和复活条件；
- 开放义务、门禁与所有者；
- 接收者的下一接受谓词；
- 发出和接收时的规范修订号；
- 接收确认或拒绝原因。

### PF-014-05：声明原子与向量化成熟度

不得只存储一个全局 `SOLVED` 或 `VERIFIED` 标志。每个可决定声明原子应独立记录：

- 精确来源、版本、解释、定义、量词和范围；
- 支持、反驳、未决和被替代关系；
- 自然语言声明到检查器或形式定理的绑定；
- 论文 v0.14 的六个证据维度：过程来源、工件可得性、确定性验证、独立审查、新颖性/先前工作、自治性/贡献归属；
- `as_of` 时间和仍未满足的义务。

证据维度不得折叠成一个总分。访问层级 E0–E5 只能描述可公开检查的工件，不是正确性分数。

### PF-014-06：相关性可见的证据与审查谱系

证据和审查必须记录模型家族、组织、编辑者、来源材料、形式化器、检查器和审查范围。相同来源生成的论文、过程叙述、代码和形式证明可以互补，但不能按文件数量冒充独立证据。

系统应能表达：

- 同模型家族或同组织相关性；
- 独立审查者的身份、范围和未检查部分；
- 贡献与正确性责任按操作拆分，而非一个全局“AI-only”标签。

### PF-014-07：验证清单必须失败关闭

形式证明和精确检查器必须保存：

- 精确命令、运行环境、依赖锁和退出状态；
- 实际执行的检查标识清单；
- 允许的公理和占位符策略；
- 必须失败的负向变异测试；
- 检查器声明的有限、符号或形式化适用域；
- 配置完成、执行完成和独立复现三个不同状态。

`assert` 被优化掉、超时、死分支、解析失败、未知状态或空输出都不得产生成功结论。

### PF-014-08：可信挑战和证书覆盖矩阵

对于 Lean/Comparator 类发布，必须区分挑战文件中的有意占位符和解答文件中的未完成证明，并建立以下映射：

```text
公开标题
→ 稿件声明原子
→ 解答模块
→ formalization 主结果
→ Comparator/可信挑战配置
→ 命名定理与绑定定义
→ 允许公理、内核与第二内核执行状态
```

未覆盖的子声明必须显式保留为开放义务。仓库存在、顶层构建成功、主结果登记和 Comparator 命名覆盖是四种不同证据。

### PF-014-09：仓库快照谱系

每次以仓库作为证据时必须记录：

- 仓库 URL、分支或标签、解析后的提交哈希和观察时间；
- 父提交数量、先前已审计提交；
- 新旧快照关系：后代、替代、被替代或未知；
- 构建命令、依赖锁、构建日志和独立复现状态。

仓库快照变化首先是 Artifact State 变化，不得自动升级或降级 Claim State。

### PF-014-10：修复与替代谱系

形式化器、模型或人工修改论证时必须标注其关系：转录、补全、局部修复、替代、重定目标或仅编辑表述。应记录：

- 输入与输出工件哈希；
- 改动的声明原子和承重步骤；
- 原论证是否仍被保留；
- 哪些旧证据失效、哪些仍然有效；
- 需要重新打开的下游义务。

### PF-014-11：结果层级与依赖图

数据模型必须区分研究 episode、结果家族、共享方法/依赖边、声明原子、稿件章节、形式目标包、源码文件和挑战配置。统计和发布不得把这些嵌套对象相加成独立成功数量。

### PF-014-12：尝试分母、无变化回合和成本向量

项目应保留预注册目标集以及失败、超时、重复、撤回、作用域无效和无变化的尝试。成本至少拆分为：

- 发现推理与工具成本；
- 失败尝试；
- 人工选择、语义绑定和审查；
- 稿件整理；
- 形式化与检查；
- 独立复现与外部审查；
- 基础设施成本。

不得用“发现 token 价格”代表完整生命周期成本。

### PF-014-13：微型证伪和基准完整性

扩大搜索或形式化之前，应记录最便宜的反例探针、边界实例、参数范围、极限次序以及最强相关优化基准。只超过较弱基准不能被描述为超过当前最佳结果。

### PF-014-14：Research Episode Dossier

系统应能从规范事件和内容寻址工件生成论文 v0.14 第 1513–1565 行所列的 27 项发布档案。每一字段必须标记来源：规范事件、可重建投影、人工声明或回顾性重构。缺失信息写为 unknown/absent，不进行推断。

### PF-014-15：可选问题议程只属于搜索来源

如果加入视角引导的问题生成，应保存视角来源、问题父子关系、追问深度、人工引导、概念图修改、提纲冻结/重开和来源偏差审计。问题数量、人格数量或概念图密度不得被计为数学进展或独立审查。

### PF-014-16：并发、门禁与权限不变量

- 状态写回使用预期修订号、幂等键和原子提交；
- 并发工作使用作用域租约或等价机制，防止陈旧状态覆盖；
- 门禁只能由声明的权限和证据满足，旁支工作不能把主门禁隐藏为“已完成”；
- todo 所有权、数学验证权和发布批准权必须分离；
- 所有投影必须能追溯到规范事件修订并检测漂移。

## 3. 对现有 Alpha.4 文档的影响

| 文档或边界 | 保留内容 | 下一版本需要增加 |
|---|---|---|
| Alpha.4 发布和迁移说明 | 作为历史记录原样保留 | 不追写为 Alpha.4 已具备 v0.14 能力 |
| `ARCHITECTURE.md` | K0、P0–P10、事件溯源、12 个 SIP 模块 | 四状态平面、转移接受、延续合同、声明/证据/验证/快照层 |

| 发布验证 | 测试、Schema、构建、哈希 | 干净工作树、覆盖矩阵、执行清单、快照谱系、负向变异、档案完整度 |

## 4. 实施与兼容原则

1. 新能力通过新事件类型、新对象和新投影实现，不改写 Alpha.1–Alpha.4 事件。
2. 现有 `Route`、`Challenge`、`BridgeResult`、`DeadEndConstraint`、`ResearchCheckpoint`、`ModelSession` 和 `HandoffArtifact` 保持可读；必要时通过关联对象补充语义。
3. 历史自由文本不能自动升级为已接受状态；迁移只能标记为 `LEGACY_UNCLASSIFIED`、`AUTHOR_REPORTED` 或等待人工确认。
4. 不把论文中的描述性观察伪装成已经验证的产品收益。动态控制平面和问题议程必须通过等预算实验评估。
5. 任何发布声明都必须说明当前实现覆盖了哪些 PF-014 要求，以及哪些仍未完成。

- 本规范；
- 更新后的目标架构；
- 逐项软件差距审计；
- 带依赖、验收条件和非回退约束的升级计划；
- 下一版本验收矩阵。
